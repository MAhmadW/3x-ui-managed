**3X-UI Managed** is a fork of [3X-UI](https://github.com/MHSanaei/3x-ui), the web control panel for [Xray-core](https://github.com/XTLS/Xray-core) by [MHSanaei](https://github.com/MHSanaei) and its contributors. The panel itself is upstream's work; this fork changes how it is packaged and deployed.

The fork targets **managed container platforms**: services that run a single container, give it no host networking or extra kernel capabilities, and expose **one HTTP port** (80/443) behind their own HTTPS edge. Stock 3X-UI assumes a server where the panel, the subscription server and every inbound each get their own port. Here, the panel and the VPN connections share the one port the platform provides.

> [!IMPORTANT]
> Before deploying, read the terms of service and acceptable-use policy of the platform you are deploying to, and follow them. Many hosting platforms restrict or prohibit proxy and VPN workloads. Compliance is your responsibility.
>
> As with upstream, this project is intended for personal use only. Do not use it for illegal purposes or in a production environment.

## Getting started

- **[SETUP.md](SETUP.md)** — deploy to a platform and get one working VLESS connection on port 443, with the problems we hit along the way.
- **[managed/README.md](managed/README.md)** — how the single-port image works, every setting, and how to run it locally with Docker Compose.

The repository's `Dockerfile` builds the single-port image by default. `docker build --target upstream .` builds the stock 3X-UI image.

## What works, and what does not

Behind a platform's HTTPS edge, the platform terminates TLS and forwards plain HTTP to the container. That decides which protocols are usable.

**Works**

- **VLESS over an HTTP-based transport**: XHTTP (recommended), WebSocket (deprecated by Xray) or HTTPUpgrade.
- The panel, on a sub-path of the same hostname.
- Subscriptions, on the same hostname.

Only VLESS has been tested. Other protocols that can ride the same HTTP transports may work but are unverified.

**Does not work behind an HTTPS edge**

- **REALITY** and **XTLS-Vision / raw TCP**: they need the client's raw TLS or TCP stream, which the platform consumes.
- **gRPC transport**: needs HTTP/2 end to end, which many platform edges do not provide.
- **Anything UDP-based**: mKCP, Hysteria2, TUIC, WireGuard and AmneziaWG.
- **Protocols with their own listener on a raw port**: MTProto, Shadowsocks, and plain HTTP/SOCKS inbounds.

**Other limits to know about**

- **The platform can observe your traffic's metadata.** TLS ends at the platform's edge, so between the edge and your container the platform can see the client identifier and the destinations of connections. Content that is itself encrypted (HTTPS) stays encrypted to the destination.
- **No Fail2ban enforcement.** IP-limit bans need the `NET_ADMIN` capability, which managed platforms do not grant.
- **Long-lived connections are at the platform's mercy.** Idle timeouts, maximum request durations and request buffering vary by platform.
- **Storage must be persistent.** Without a mounted volume or an external PostgreSQL database, every deploy wipes users and inbounds, including a deploy triggered by a push to the repository.

## The setup that worked for us

- **Mode:** edge mode (`PROXY_MODE=edge`, the default). The platform terminates TLS and forwards plain HTTP to one container port.
- **Platform:** a managed container platform, running one service with a persistent volume mounted at `/etc/x-ui`.
- **Panel:** served on an unguessable sub-path of the service's public HTTPS domain.
- **VPN:** one VLESS inbound over XHTTP, reached on port 443 of the same domain, with TLS provided by the platform.
- **Client:** v2rayN on macOS, importing the share link generated by the panel.

### Platforms that work in edge mode

Edge mode fits any platform that gives a container a public HTTPS domain and forwards the requests to it as plain HTTP on one port. Examples of platforms built this way:

- Azure Container Apps
- DigitalOcean App Platform
- Fly.io
- Google Cloud Run
- Koyeb
- Northflank
- Railway
- Render

This list describes how these platforms route traffic, nothing more. It is not a statement that any of them permits proxy or VPN workloads, and several restrict them; read each platform's terms before deploying. The fork has not been tried on every platform listed, and details such as persistent storage, idle timeouts and request buffering differ between them.

### Platforms that work in direct mode

Direct mode (`PROXY_MODE=direct`) is for hosts that pass TCP port 443 to the container untouched. The container terminates TLS itself, with a certificate Caddy obtains automatically, so it needs a domain name pointing at it and persistent storage for the certificate. Examples:

- **Any VM or VPS running Docker**: AWS EC2, Azure Virtual Machines, DigitalOcean Droplets, Google Compute Engine, Hetzner Cloud, Linode, Oracle Cloud, Vultr.
- **Container services with TCP passthrough**: AWS ECS or Fargate behind a Network Load Balancer, Azure Container Instances with a public IP, Fly.io with a raw TCP service, or Kubernetes with a `LoadBalancer` service.

Compared with edge mode, the host no longer sees inside the TLS connection, but the usable transports are the same HTTP-based ones, because this image still routes by URL path. The same caution about each provider's terms applies.

Direct mode has only been tested locally, with a locally-signed certificate. It has not been run against a public domain on any of the hosts above. On a VM where you control every port, stock [3X-UI](https://github.com/MHSanaei/3x-ui) is also an option and supports every protocol; direct mode is for keeping everything on 443.

## Panel features (from upstream)

The feature list below describes the 3X-UI panel as a whole. On a managed platform, only the subset described above is reachable from outside the container.

- **Multi-protocol inbounds** — VLESS, VMess, Trojan, Shadowsocks, WireGuard, AmneziaWG, TUIC v5, Hysteria2, MTProto, HTTP, SOCKS (Mixed), Dokodemo-door / Tunnel, and TUN.
- **Modern transports & security** — TCP (Raw), mKCP, WebSocket, gRPC, HTTPUpgrade, and XHTTP, secured with TLS, XTLS, and REALITY.
- **AmneziaWG built in** — DPI-resistant WireGuard runs inside the panel on a userspace network stack, with no kernel module, DKMS, or extra packages to install.
- **Native TUIC v5 server** — In-process Go QUIC server with Xray routing and per-client traffic accounting; BBR and New Reno are available server-side. CUBIC is preserved in the client profile but currently falls back to New Reno on the server.
- **MTProto proxies** — per-client FakeTLS secrets, ad-tags, and quotas, applied live without dropping existing connections.
- **Fallbacks** — serve multiple protocols on a single port (e.g. VLESS and Trojan on 443) using Xray's fallback support.
- **Per-client management** — traffic quotas, expiry dates, IP limits with trusted-address exemptions, HWID device limits, scheduled renewal cycles, live online status, and one-click share links, QR codes, and subscriptions.
- **Traffic statistics** — per inbound, per client, and per outbound, with reset controls.
- **Multi-node support** — manage and scale across multiple servers from a single panel, including cloning inbounds onto other nodes.
- **Outbound & routing** — WARP, NordVPN, PIA, custom routing rules, load balancers with balancer-to-balancer fallback, and outbound proxy chaining. Bundled geosite and geoip categories are browsable straight from the rule editor.
- **Built-in subscription server** — raw, JSON, and Clash output, auto-selected from the client's User-Agent, plus [custom page templates](docs/custom-subscription-templates.md).
- **Telegram and Discord bots** for remote monitoring and management.
- **RESTful API** with scoped, optionally expiring tokens and an in-panel API reference.
- **Installable panel (PWA)** — pin 3X-UI to a desktop or phone home screen.
- **Flexible storage** — SQLite (default) or PostgreSQL.
- **14 UI languages** with dark and light themes.
- **Fail2ban integration** for enforcing per-client IP limits.

## Installing on a regular server

This fork does not publish releases or an installer. For a normal VPS install, where each inbound gets its own port and every protocol is available, use [upstream 3X-UI](https://github.com/MHSanaei/3x-ui) and its [documentation](https://docs.sanaei.dev).

## Database Options

3X-UI supports two backends, chosen during the install:

- **SQLite** (default) — a single file at `/etc/x-ui/x-ui.db`. Zero setup, ideal for small and medium deployments.
- **PostgreSQL** — recommended for high client counts or multi-node setups. The installer can install PostgreSQL locally for you, or accept a DSN to an existing server.

At runtime the backend is selected via environment variables (the installer writes these to `/etc/default/x-ui` for you):

```
XUI_DB_TYPE=postgres
XUI_DB_DSN=postgres://xui:password@127.0.0.1:5432/xui?sslmode=disable
```

### Migrating an existing SQLite install to PostgreSQL

```bash
x-ui migrate-db --dsn "postgres://xui:password@127.0.0.1:5432/xui?sslmode=disable"
# then set XUI_DB_TYPE and XUI_DB_DSN in /etc/default/x-ui and restart:
systemctl restart x-ui
```

The source SQLite file is left untouched; remove it manually once you have verified the new backend.

### Docker

This section is about the stock image, which `docker-compose.yml` builds. The single-port image is run with `docker-compose.managed.yml` instead and has Fail2ban off; see [managed/README.md](managed/README.md).

The default `docker compose up -d` keeps using SQLite. To run with the bundled PostgreSQL service, uncomment the two `XUI_DB_*` env lines in `docker-compose.yml` and start with the profile:

```bash
docker compose --profile postgres up -d
```

The image bundles Fail2ban (enabled by default) to enforce per-client **IP limits**. Fail2ban bans offenders with `iptables`, which requires the `NET_ADMIN` capability. `docker-compose.yml` already grants it via `cap_add`; if you start the container with `docker run` instead, add the capabilities yourself, otherwise bans are logged but never applied:

```bash
docker run -d --cap-add=NET_ADMIN --cap-add=NET_RAW ... ghcr.io/mhsanaei/3x-ui
```

## Environment Variables

| Variable | Description | Default |
| --- | --- | --- |
| `XUI_DB_TYPE` | Database backend: `sqlite` or `postgres` | `sqlite` |
| `XUI_DB_DSN` | PostgreSQL connection string (when `XUI_DB_TYPE=postgres`) | — |
| `XUI_DB_FOLDER` | Directory for the SQLite database file | `/etc/x-ui` |
| `XUI_DB_MAX_OPEN_CONNS` | Maximum open connections (PostgreSQL pool) | — |
| `XUI_DB_MAX_IDLE_CONNS` | Maximum idle connections (PostgreSQL pool) | — |
| `XUI_INIT_WEB_BASE_PATH` | The initial URI path for the web panel | `/` |
| `XUI_ENABLE_FAIL2BAN` | Enable Fail2ban-based IP-limit enforcement | `true` |
| `XUI_LOG_LEVEL` | Log verbosity (`debug`, `info`, `warning`, `error`) | `info` |
| `XUI_DEBUG` | Enable debug mode | `false` |
| `XUI_TUNNEL_HEALTH_MONITOR` | Enable the tunnel health monitor (probes a URL and restarts xray after repeated failures; a restart drops all clients) | `false` |
| `XUI_TUNNEL_HEALTH_PROXY` | Proxy the probe is sent through; point it at a local xray inbound so the probe tests the tunnel (e.g. `socks5://127.0.0.1:1080`). Empty means the probe only checks host connectivity | — |
| `XUI_TUNNEL_HEALTH_URL` | URL probed for tunnel health | `https://www.cloudflare.com/cdn-cgi/trace` |
| `XUI_TUNNEL_HEALTH_INTERVAL` | Interval between probes | `30s` |
| `XUI_TUNNEL_HEALTH_TIMEOUT` | Per-probe timeout | `10s` |
| `XUI_TUNNEL_HEALTH_FAILURES` | Consecutive failures before a restart is triggered | `3` |
| `XUI_TUNNEL_HEALTH_COOLDOWN` | Minimum delay between consecutive restarts | `5m` |
| `NODE_TOKEN_ENCRYPTION` | Encryption at rest for node API tokens: `off`, `migration`, or `required` (note: no `XUI_` prefix) | `off` |
| `XUI_NODE_TOKEN_KEY_FILE` | JSON keyring (mode `0600`) holding the active key id and its base64 32-byte keys | `/etc/x-ui/node_token_key.json` |
| `XUI_NODE_TOKEN_KEY` | A single base64 32-byte key, used only when the key file cannot be loaded | — |

The complete list is on the [environment variables reference](https://docs.sanaei.dev/docs/reference/env-vars).
